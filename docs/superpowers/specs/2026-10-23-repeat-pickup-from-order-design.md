# Повтор выноса прямо из оформления заказа

Дата: 23 октября 2026

## Задача

Завести расписание сейчас можно только на отдельной странице, где форма просит
адрес, шесть полей деталей, описание, заметки, частоту, время, дни недели и две
даты — четырнадцать полей ради «выносите мусор по вторникам». При этом обычный
заказ оформляется выбором сохранённого адреса в два клика.

Переносим создание расписания туда, где человек уже всё это указал: в форму
заказа.

## Решение

### Где

Блок «Повторять этот вынос» внизу формы оформления заказа
(`CreateOrderModalWithTabs`), виден только при активной подписке — расписания
доступны лишь подписчикам, остальным блок не показывается.

Содержимое блока: переключатель, четыре варианта частоты (каждый день, через
день, раз в неделю, свои дни недели), кнопки дней недели для последнего
варианта, строка с человеческим пересказом результата и напоминание об остатке
лимита подписки.

Адрес, детали адреса и время расписание берёт из самого заказа — отдельных
полей нет.

### Как создаётся

Фронт делает два запроса: `POST /orders`, затем `POST /scheduled-orders`.

Рассматривали вариант с полем `repeat` внутри `CreateOrderDto`, чтобы бэкенд
заводил расписание сам в одной транзакции. Отклонён: `ScheduledOrdersService`
уже зависит от `OrderService` (заказы по расписанию идут общим путём), и
обратная зависимость даёт цикл модулей, который лечится только `forwardRef`.

Цена выбранного варианта — заказ может создаться, а расписание нет. Тогда заказ
остаётся, а человек видит сообщение «Заказ создан, но повтор сохранить не
удалось» со ссылкой на страницу расписаний.

### Первый вынос не должен задвоиться

Клиент заказывает вынос на завтра 10:00 и просит повторять каждый день. Если
завести расписание с `startDate` = завтра, ночью крон создаст на завтра второй
заказ — тот же самый вынос, уже оформленный руками.

Поэтому `CreateScheduledOrderDto` получает флаг `firstPickupAlreadyOrdered`.
При нём сервис проставляет `lastCreatedAt = startDate`, и `findDueOccurrence`
пропускает этот вынос: первым автоматическим станет следующий по частоте.

### Адрес

`CreateScheduledOrderDto` получает `addressId`. Расписание хранит его и передаёт
в `OrderService.create`, который уже умеет проверять принадлежность адреса
клиенту. При создании расписания адрес проверяется сразу, чтобы ошибка не
всплыла ночью через крон.

Это заодно закрывает старую дыру: у заказов по расписанию `addressId` не было
вовсе, адрес хранился текстом.

### Страница «Расписания»

Остаётся, но только для управления: список с датой следующего выноса, пауза,
удаление, правка частоты, дней и времени. Большая форма создания убирается,
кнопка ведёт на оформление заказа. Адрес у существующего расписания не меняется
— для другого адреса заводится другое расписание.

## Границы

- Тарифов подписки на проде нет, поэтому проверить блок вживую можно будет
  только после того, как они появятся.
- Расписание по-прежнему создаёт заказы ровно на 2 пакета — как и раньше.

## Проверка

- Тест на то, что расписание с `firstPickupAlreadyOrdered` не создаёт заказ на
  уже оформленный вынос, рядом с тестами `findDueOccurrence`.
- Тест на отказ по чужому `addressId`.
- Фронт — вручную в браузере: тестов на нём нет.
